# Conversation research inheritance — first bounded protocol

This implements application-level answer capability evolution, **not foundation-model training or guaranteed general intelligence improvement**. Hosted Pollinations weights remain inaccessible. No user conversation is copied into public research records.

## Actual loop

1. A read-only proposer freezes the current accepted parent hash and the next capability from a fixed finite DSL. Initially: exact integer arithmetic, then metric length conversion. Proposals are data, never executable source or arbitrary system prompts.
2. A separate read-only validation job generates eight new samples after freezing, using a new random seed. Python integer/Decimal arithmetic is the independent answer oracle. Baseline and candidate receive the same task. An inactive capability calls the existing anonymous inference endpoint; an active one uses the tested deterministic compiler.
3. Acceptance requires all eight candidate answers exact, no correctness regression, every baseline call completed, and either more correct answers or at least four paired results faster by over 50% plus 20 ms. Provider failures alone cannot produce adoption. Research requests wait at least 30 seconds after the previous completed pair, with at most one recovery attempt after 35 seconds. All attempts and timing are retained. A trial has a 600-second budget. These timings describe this evaluation environment, not promised iPhone latency.
4. A separate write job recomputes acceptance and checks the current parent. Only fixed dialogue data paths in research-records can change; no main update, validator modification, threshold relaxation or candidate credential. Publication uses GitHub's job-scoped token, not a user-provided API key.
5. The chat server reads the accepted artifact, validates its hash, schema, evidence and local regression probes, then uses it in actual /api/chat responses. Generation, policy hash and mode are reported. Fresh processes inherit the same accepted generation. On read/network failure the healthy loaded version is preserved. A capability regression selects a passing historical policy or baseline and quarantines the failed artifact in that process; this guard repeats on fresh load.
6. Research continues every six hours and after verified releases. Once the finite capability space is exhausted it monitors rather than pretending new generations are improvements. Extending trusted capabilities or evaluation criteria needs a separately reviewed, tested PR.

## Routing boundary

Only a full, short integer expression (+, -, ×, exact integer division), or a supported mm/cm/m conversion is intercepted. No eval, dynamic imports, arbitrary code, web fetching, floating-point arithmetic, exponentiation, fractional division or zero division. In a continuing conversation, explicit `計算:` is required; otherwise the external model retains conversation context. Other prompts retain ordinary chat behavior. Accepted research metadata is supplied as factual system context, with an explicit statement that weights were not trained.

Examples once the corresponding generation is accepted:
- New chat: `9007199254740993 + 2`
- Existing chat: `計算: 12345678 × 23456`
- Metric capability: `計算: 1.25 m を mm に換算`

## What this does not prove

The proposer does not invent arbitrary new algorithms. A latency gain is not a measured intelligence gain. Eight randomly generated cases plus unit tests are finite evidence, not universal proof or independent external replication. Existing research-model weight learning remains a separate experiment. No physical iPhone, RSI, endless evolution or permanent availability claim.

Development trial encountered a keyless-provider refusal on its second baseline call; it was rejected/deferred. No production artifact was installed from that trial. PR and production workflow records are authoritative for subsequent adoption decisions.

Candidate browser evaluation completed two chat turns but the following arithmetic API call received KEYLESS_UNAVAILABLE. Production inference is therefore serialized with a 16-second cooldown after completion, instead of overlapping requests with only start-slot pacing. This is a quota-conservative recovery measure, not proof of the upstream refusal cause.
